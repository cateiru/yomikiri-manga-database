# 実装プラン 006: デプロイ・運用

## 概要

Web を Cloudflare Workers へ、バッチをさくらVPS へ配備し、
定期実行と CD（自動デプロイ）を含む運用体制を整える。
CI 自体は [007 ローカル開発環境・CI](./007_ローカル開発環境・CI.md) で設定済みの前提とする。

- 参照: [001_plan.md 8.1 章「実行環境」](../001_plan.md)、[11 章「非機能要件・留意事項」](../001_plan.md)

## 実装タスク

### 1. Cloudflare Workers（apps/web）

- `wrangler.jsonc` を本番用に整備する（プラン 004 で作成済みの設定を拡張）
- `DATABASE_URL` を `wrangler secret put` で登録する
- `opennextjs-cloudflare build && wrangler deploy` によるデプロイスクリプトを
  `package.json` に定義する
- ISR（`revalidate: 300`）が Workers 上で機能することを確認する
- カスタムドメインの割り当て（用意できる場合）

### 2. さくらVPS（apps/batch、Docker）

- Docker / Docker Compose をセットアップする（Node.js を VPS に直接インストールする必要はない）
- バッチは `apps/batch/Dockerfile` でイメージ化する。本番用の `compose.prod.yaml`
  （ローカル開発用の `compose.yaml` とは別ファイル。`db` / `wsproxy` は含まず `batch` / `ofelia` を定義）の
  `batch` サービスを `docker compose -p app -f compose.prod.yaml run --rm batch` として
  都度起動・都度破棄する形で実行する
  - `restart: always` による常駐化は採用しない。バッチは 1 回実行して終了する oneshot 処理のため、
    常駐させると正常終了のたびに即座に再起動され「毎日 00:05・12:05・18:05（JST）」の実行スケジュールと両立しない
- スケジューリングは ofelia（Docker コンテナ用の軽量 cron スケジューラ、`deploy/ofelia/Dockerfile` で
  docker CLI + compose プラグインを追加した独自イメージ）が担う。`compose.prod.yaml` の `ofelia`
  サービスが `docker compose up -d` で常駐し、`job-local` ジョブ（labels で定義）が
  毎日 00:05・12:05・18:05（JST）に `deploy/bin/run-batch.sh` を実行する
  - `run-batch.sh` が `docker compose -p app -f compose.prod.yaml run --rm batch` を実行し、
    標準出力・標準エラーを `/var/log/yomikiri/batch.log` にリダイレクトしつつ、
    成功時のみ `/var/lib/yomikiri/last-success` を、失敗時は `/var/lib/yomikiri/last-failure` を touch する
  - ofelia コンテナは `/opt/yomikiri/app`・`/var/lib/yomikiri`・`/var/log/yomikiri`・
    `/etc/yomikiri/batch.env`・`/var/run/docker.sock` をホストと同一パスで bind mount する
    （ホストと同一パスにすることで symlink 経由の誤タグ事故を構造的に排除する）
  - systemd timer の `Persistent=true`（VPS 停止中に見逃した実行を起動時に自動キャッチアップする機能）に
    相当する仕組みは無い。追加するとデプロイ（`up -d ofelia`）のたびに追加のクロールが発生してしまうため、
    この機能欠落は受け入れる。実運用上の影響は、実行タイミングをまたいだ場合にその回のバッチが
    1 回スキップされ、次のスケジュールで自動的に復帰するのみ
- デプロイ方法: VPS 上で `git pull` + `docker compose -p app -f compose.prod.yaml build batch ofelia mackerel-agent` +
  `docker compose -p app -f compose.prod.yaml up -d` を行う簡易スクリプト
  （`deploy/bin/deploy.sh`）を用意する。`batch` は `profiles: ["batch"]` で縛られているため、
  bare な `up -d` でも常駐せず、`ofelia`・`mackerel-agent`・`otelcol-mackerel` のみが対象になる。
  `up -d` は labels（スケジュール等）の変更を反映するために毎回実行する
  （Docker のコンテナラベルは実行中に変更できないため）。
  デプロイ実行は 00:05・12:05・18:05 の実行時間帯を避ける
  （実行中の `run-batch.sh` と重なると `last-success` が更新されないまま実行が終わる可能性がある）
- `DATABASE_URL` は環境ファイル（`/etc/yomikiri/batch.env`、パーミッション 600）で管理する。
  `compose.prod.yaml` の `batch` サービスが `env_file:` でこれを直接読み込む
  （`env_file` は compose のクライアント側で解決されるため、ofelia コンテナにも
  同じパスで bind mount しておく必要がある）
- 監視は Mackerel（`mackerel-agent`）で行う。mackerel-agent・otelcol-mackerel（後述のログ収集）は
  いずれもホストへ直接インストールせず、`compose.prod.yaml` の `mackerel-agent` /
  `otelcol-mackerel` サービスとして Docker コンテナで動かす
  （`deploy/mackerel-agent/Dockerfile` は公式イメージ `mackerel/mackerel-agent` に
  docker CLI + compose プラグインを追加しただけの薄いラッパー。後述の
  `yomikiri-ofelia-service` チェックが `docker compose ps` を叩くために必要）
  - check プラグイン設定（`deploy/mackerel/yomikiri-batch-checks.conf`）は
    `mackerel-agent` コンテナの `/etc/mackerel-agent/conf.d/` に bind mount し、
    `include` 環境変数（= mackerel-agent.conf 内の include 設定）経由で読み込ませる。
    `[plugin.checks.*]` が conf.d 経由（include）では読み込まれないという情報が
    一部にあるが、mackerelio/mackerel-agent の実装（`includeConfigFile` が include
    先ファイルにも `setEachPlugins()` を呼び直す）と実機検証の両方で「conf.d + include
    で正しく読み込まれる」ことを確認済み
  - `check-file-age` プラグインで `/var/lib/yomikiri/last-success` の鮮度を監視し、
    13 時間（最大実行間隔 12 時間 + マージン）以上更新がなければ警告、16 時間以上でクリティカルとする
    （実行漏れ・ハングの検知）。`check-file-age` は `mackerel/mackerel-agent` イメージに
    標準で同梱されている `mackerel-check-plugins` パッケージに含まれるため、別途インストール不要
  - `last-failure` が `last-success` より新しいかを確認するカスタムチェックで、
    直近の実行失敗を検知する（`run-batch.sh` が失敗を検知できた場合のみ機能する。
    ofelia コンテナ自体の異常終了はこのチェックでは拾えないため、`ofelia` コンテナの
    死活監視チェックを別途用意し、残るギャップの一部をカバーする）
  - Mackerel 上のホスト ID は `/var/lib/mackerel-agent/`（コンテナへも同一パスで
    bind mount）に永続化される。デプロイのたびに `up -d` でコンテナが再作成されても
    同一ホストとして認識され続ける。`auto_retirement` は設定しない
    （有効にすると `up -d` のたびに VPS ホストが retire されてしまう）
  - `hostname` は compose 側で固定しない（Docker が割り当てるコンテナ ID 風の名前が
    Mackerel 上の表示名になる）。`${VAR:?}` 形式の必須変数をこのファイルに使うと、
    docker compose がファイル全体を interpolate する仕様上、ofelia コンテナ内の
    `run-batch.sh` や `yomikiri-ofelia-service` チェックなど、このファイルに対する
    他の compose 呼び出しまで軒並み失敗する（実機検証で確認済み）ため使わない
- ログは `/var/log/yomikiri/batch.log`（`run-batch.sh` のリダイレクト先）で確認する。
  バッチコンテナは `--rm` で実行のたびに破棄されるため、`docker compose logs` は
  実行中の一時的な確認にしか使えない
- 加えて、Mackerel の新ログ機能（β、OTel Collector 経由）を使い、`/var/log/yomikiri/batch.log` を
  Mackerel 上でも検索・閲覧できるようにする。`otelcol-mackerel`（MDOT Collector）もホストへ
  直接インストールせず、公式イメージ `mackerel/otelcol-mackerel` をそのまま
  `compose.prod.yaml` の `otelcol-mackerel` サービスとして使う（ビルド不要）。`filelog`
  receiver でそのファイル 1 本のみを読む → （JSON パース）→ Mackerel への転送パイプラインを
  構成する（設定は `deploy/mackerel/otelcol-mackerel-config.yaml`。コンテナの
  `/home/nonroot/config.yaml` に bind mount し、CMD で `--config /home/nonroot/config.yaml`
  を渡して読み込ませる）。対象ファイルを 1 本に限定することで、無料枠（月 1GB）の超過事故を防ぐ。
  既存の `check-file-age` / `last-failure` によるチェック監視（死活監視）とは別軸の仕組みであり、
  互いに独立して動作する
  - file_storage extension（Collector 再起動時の読み取りカーソル永続化）は使わない。
    `mackerel/otelcol-mackerel` ディストリビューションにこのコンポーネントが含まれていない
    （実機で起動し `unknown type: "file_storage"` エラーになることを確認済み。upstream の
    manifest.yaml にも extensions セクションが無い）ため、再起動中に出力されたログが
    再起動後に再読込されない制約を受け入れる（`start_at: end` のため）

#### VPS セットアップ手順

0. 事前確認（初回のみ、環境固有の前提を確認する）
   - `mcuadros/ofelia` の `job-local` が Docker labels で設定可能かを確認する
     （非対応の場合は `deploy/ofelia/config.ini` を mount する INI 方式にフォールバックする）
   - `deploy/ofelia/Dockerfile` / `deploy/mackerel-agent/Dockerfile` でビルドしたイメージ内で
     `docker compose version` が動作することを確認する（ベース OS の互換性含む。
     `deploy/mackerel-agent/Dockerfile` はローカルで一度ビルド・動作確認済み）
   - ofelia の cron スケジュール書式（フィールド数）を確認する
1. Docker / Docker Compose をインストールする
2. リポジトリを配置する: `git clone <repo-url> /opt/yomikiri/app`
3. 秘匿情報を配置する
   ```sh
   sudo mkdir -p /etc/yomikiri
   sudo tee /etc/yomikiri/batch.env <<'EOF'
   DATABASE_URL=postgres://...
   EOF
   # apikey=... の1行のみ（mackerel-agent 側の環境変数名は小文字の "apikey"）
   sudo tee /etc/yomikiri/mackerel-agent.env <<'EOF'
   apikey=<Mackerel API キー>
   EOF
   # MACKEREL_APIKEY=... の1行のみ（otelcol-mackerel 側は otelcol-mackerel 公式イメージが
   # 読む環境変数名 "MACKEREL_APIKEY" に合わせる）
   sudo tee /etc/yomikiri/otelcol-mackerel.env <<'EOF'
   MACKEREL_APIKEY=<Mackerel API キー>
   EOF
   sudo chmod 600 /etc/yomikiri/batch.env /etc/yomikiri/mackerel-agent.env /etc/yomikiri/otelcol-mackerel.env
   ```
4. 状態・ログディレクトリを用意する:
   ```sh
   sudo mkdir -p /var/lib/yomikiri /var/log/yomikiri /var/lib/mackerel-agent
   ```
   `/var/lib/mackerel-agent` は mackerel-agent コンテナが Mackerel 上のホスト ID を
   永続化する場所（`compose.prod.yaml` の `mackerel-agent` サービスが同一パスで bind mount する）
5. logrotate 設定を配置する
   ```sh
   sudo cp /opt/yomikiri/app/deploy/logrotate/yomikiri-batch /etc/logrotate.d/yomikiri-batch
   ```
6. 全イメージをビルドし、常駐サービス（ofelia・mackerel-agent・otelcol-mackerel）を起動する
   ```sh
   cd /opt/yomikiri/app
   docker compose -p app -f compose.prod.yaml build batch ofelia mackerel-agent
   docker compose -p app -f compose.prod.yaml up -d
   docker compose -p app -f compose.prod.yaml logs -f ofelia   # スケジュール読み込み・次回実行時刻を確認
   docker compose -p app -f compose.prod.yaml logs -f mackerel-agent otelcol-mackerel   # 起動エラーが無いことを確認
   ```
   - Mackerel の「ホスト」画面で新規ホストが登録されること（表示名は Docker が
     割り当てたコンテナ ID 風の名前になる）、check プラグイン
     （`yomikiri-batch-freshness` 等）が表示されることを確認する
   - `deploy/mackerel/otelcol-mackerel-config.yaml` の `transform` processor は
     `filelog` レシーバーが渡してくる body（`logger.ts` が出力する JSON 行そのもの）を
     デコードし、`level`/`message` 等をフィールドとして展開する
     （`severity_text`/`severity_number` も `level` から設定する。詳細はファイル内のコメントを参照）
   - Mackerel の新ログ機能（β）を使うには、着手前に Mackerel 組織側でログ機能（β）が
     有効になっているか（「ログ」画面が存在するか）を確認しておくこと
7. 動作確認: `docker exec` 等を使わず、`run-batch.sh` を直接叩いて手動起動する
   ```sh
   sudo /opt/yomikiri/app/deploy/bin/run-batch.sh
   ```
   `/var/lib/yomikiri/last-success` が更新されること、`/var/log/yomikiri/batch.log` に
   JSON ログが出力されることを確認する。あわせて Mackerel の「ログ」画面で該当ホストを検索し、
   `yomikiri-batch` 由来のログが `level`/`message` 等のフィールド付きで表示されること、
   他プロセスのログが混入していないことを確認する

#### 既存のホストインストール環境からの移行

mackerel-agent・otelcol-mackerel を deb パッケージでホストへ直接インストールしていた
（旧バージョンの本ドキュメントの手順に沿ってセットアップ済みの）場合、コンテナ版と
同一のホスト ID を使って二重に Mackerel へレポートしてしまうのを避けるため、
コンテナを起動する前にホスト側のユニットを停止・無効化する（パッケージ自体は残してよい。
アンインストールは不可逆なので同じデプロイでは行わない）。

```sh
sudo systemctl disable --now mackerel-agent otelcol-mackerel
```

`mackerel-agent` コンテナは `/var/lib/mackerel-agent`（ホストインストール版と同一パス）を
bind mount するため、ホスト ID ファイルがそのまま引き継がれ、Mackerel 上では
同一ホストとして認識され続ける（新規ホストとして重複登録されない）。

### 3. マイグレーション自動化・CD（GitHub Actions）

- `packages/db` のマイグレーションは `.github/workflows/migrate.yml` で自動運用する
  - CI（`ci.yml`）が main への push で成功したことを `workflow_run` でトリガーとして受け取り、
    `packages/db` に差分があるコミットのみマイグレーションジョブを実行する
    （`check-changes` ジョブで `git diff` により判定し、差分が無ければ後続の `migrate` ジョブごとスキップする）
  - `workflow_run` は fork リポジトリの CI 完了でもトリガーされ得るため、
    `event` 種別が `push` であること・`head_repository` が自リポジトリと一致することを確認してから実行し、
    secrets が意図しないコード（fork からの PR 等）に渡らないようにする
  - `concurrency`（`db-migrate-production`、`cancel-in-progress: false`）で同時多重実行を防ぐ
  - `DATABASE_URL` は GitHub Environment（`production`）の secrets から取得する
- Cloudflare Workers（apps/web）への自動デプロイワークフローは本ドキュメント作成時点で未整備。
  デプロイは `apps/web` の `pnpm deploy`（`opennextjs-cloudflare build && opennextjs-cloudflare deploy`）を
  手動実行する運用とする。GitHub Actions での自動デプロイ化は将来検討する
